```markdown
## 2026-08-17｜音声はPWA自身で録音し、文字起こしはサーバー側で行う（キーボードに依存しない）
- 決定：緑のマイク1タップで `getUserMedia` + `MediaRecorder` により**PWA自身が録音**し、`POST /api/v1/transcribe` で `gpt-4o-mini-transcribe` に文字起こしさせる。文字入力欄は「聞き取りを直す」ためだけに残し、**開いても focus しない**（キーボードを自動で出さない）
- 理由：同日の前の決定（iOSキーボードのマイクキーを本命にする）は、実機で「マイクを押すとキーボードが開く」体験になっていた。`webkitSpeechRecognition` がPWAで使えないのは変わらないが、`getUserMedia` + `MediaRecorder` はPWAでも動くため、キーボードを介さずに録音できる
- 補足：録音形式は決め打ちせず `MediaRecorder.isTypeSupported` で判定（iOSはmp4、他はwebm、どれも通らなければブラウザ任せ）。使えない端末では録音ボタンを出さず文字入力へ落とす。終了・失敗・画面離脱のどの経路でも `MediaStreamTrack.stop()` を通す。鍵は既存の `OPENAI_API_KEY` をサーバー側だけで使い、**音声はAppwrite・localStorage・通常ログのどこにも保存しない**。Realtime API / TTS / 音声アシスタント化はscope外
- 決定者：ゆま（依頼）／ジョブズ（実装判断）

## 2026-08-17｜厳しいschemaの手前に「言い方の揺れを吸収する層」を置く。ただし足りない値は推測しない
- 決定：`/api/v1/command` の検証の手前に正規化層（`api/_v1/normalize.ts`）を置き、省略形・文字列や全角の数値・**自重種目の重量0**・同一種目で省かれた続きの重量、までを吸収する。回数・種目名・加重種目の重量が本当に無い場合は**保存せず、足りない点だけ聞き返す**。検証エラーは必ず日本語へ言い換え、zodの文言を画面へ出さない
- 理由：実機で「懸垂8回と7回」のような自然な発話が `Invalid input: expected number, received undefined` で弾かれ、内部文言がそのまま画面に出ていた。schemaを緩めると誤った値が保存されうるため、schemaは据え置き、その手前で吸収する形にした
- 補足：音声の書き込みは `apply: 'client'` でサーバー保存を止め、既存の local-first / outbox を通す。`apply` 無しは従来どおりサーバー保存なので、MCP（凍結）とChatGPT経由の挙動は変わらない
- 決定者：ジョブズ（調査・実装判断）
```

```markdown
## 2026-08-17｜画面はサーバーの応答を待たない。Appwriteは正本のまま、端末に送信待ちを持つ
- 決定：画面に出す状態を `replay(base, pending)`（サーバーのスナップショット＋未送信の操作）とし、操作は即座に画面へ反映してから裏で送る。Appwriteは引き続き正本で、`LiftAndLeanService`・repository境界・既存RESTは変えない。連続入力は送信待ちの中で1件にまとめ、さらに500ms手が止まってから送る
- 理由：Appwriteを正本にしたあと、1操作ごとに往復を待つ作りになっていた。人工遅延2秒での実測で、種目追加4,046ms・食事追加2,027ms・起動2,154msかかり、目標値は入力中にサーバーの応答で4回巻き戻って最終値が壊れていた。さらに送信待ちの控えが無いため、圏外・障害中の記録は「記録しました」と表示されたまま消えていた
- 補足：控え（190KB）は間引いて書き、送信待ちは毎回すぐ書く（記録が消えては困るため）。冪等キーは端末が決めた仮idを再利用し、再送で二重登録しない。同じ送信待ちを複数タブが流さないよう送信権を持たせ、離脱時に手放す。未送信があるログアウトは件数を見せて確認する。「保存できていないものを保存済みと表示しない」ことを不変条件にした
- 決定者：ゆま（依頼）／ジョブズ（実装判断）

## 2026-08-17｜音声入力はWeb Speech APIに依存せず、iOSキーボードのマイクを本命にする
- 決定：話して記録する入口は「文字入力欄（iOSキーボードのマイクキーで音声入力）」を本命とし、`webkitSpeechRecognition` は使える環境でだけ補助として出す。サーバー側の文字起こしAPIは使わない
- 理由：2026年8月時点で `webkitSpeechRecognition` はiOS Safariのタブでは動くが、**ホーム画面に追加したPWAでは動かない**（Apple未対応）。Lift & Leanの主戦場はPWAなので、これに依存すると本人の端末で使えない。キーボードのマイクは権限も費用も追加不要で確実に動く
- 補足：出典 https://whatpwacando.today/speech-recognition/ ・ https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide 。振り分けは `POST /api/v1/command` で行い、MCPと同じ `TOOLS`・同じ入力schemaを使って二重管理しない。削除・目標変更の道具は存在させないので音声からは消せない。言語モデルの呼び出しは1指示につき1回（食事のカロリー推定も同じ1回に含める）。鍵はサーバーのみで、既存の `OPENAI_API_KEY` を使う
- 決定者：ジョブズ（調査・実装判断）
```
