# ローカル先行の記録と、話して記録する入口

Appwrite を正本にしたあと、実機で「1操作ごとに待たされる」状態になっていた。
その原因を実測で特定し、**画面が通信を待たない**作りへ変えた記録。
あわせて、ChatGPT mobile の代わりになる音声入口を足した。

MCP / OAuth は**凍結して残す**（消していない）。将来 ChatGPT mobile が
custom MCP に対応したら、同じサービス層へ戻せる。

---

## 1. 何が遅かったのか（実測）

計測は実ブラウザ（Chrome / iPhone相当・CPU 4分の1）で行い、
`tests/perf/lab-server.mjs` が `/api/v1/*` を**人工遅延つき**で再現する。
データは半年ぶん（スナップショット 191,778 バイト）。

    node tests/perf/lab-server.mjs                 # 実験サーバー
    node tests/perf/bench.mjs --label before       # 計測
    node tests/perf/compare.mjs                    # before/after を並べる

原因は7つ。いずれも「サーバーの応答を待ってから画面を書き換える」ことに由来する。

| # | 原因 | 場所 | 症状（遅延2秒のとき） |
|---|------|------|----------------------|
| 1 | 保存が往復のあと | `useAppData.run()` | 追加・編集のたびに2秒固まる |
| 2 | 保存を1本の列で直列化 | `useAppData` queue | 前の保存が終わるまで次が始まらない |
| 3 | 1打鍵ごとに書き込み | 設定の目標値 | 4文字打つと4回 PUT /goals |
| 4 | 応答が入力を巻き戻す | 目標値 | 「1850」と打つと画面が 2400 に戻り、最後は「1」 |
| 5 | 逐次2往復 | 種目追加 | POST /exercises → PUT /profile で **4,046ms** |
| 6 | 起動が毎回ブロック | `refreshAccount()` → snapshot | 控えがあっても **2,154ms** 白い画面 |
| 7 | 送信待ちの控えが無い | — | 圏外・障害中の記録が**そのまま消える** |

補足（7に関連する実害）：食事を足すと `✓ 記録` の吹き出しが
**保存の成否と関係なく即座に**出ていた。サーバーが落ちていても
「記録しました」と表示され、実際には保存されていない。

## 2. 変えたこと

### 状態の持ち方

    画面に出す状態 = replay(base, pending)

    base    … 最後にサーバーから受け取ったスナップショット
    pending … まだ送れていない操作の列（outbox）

計算後の状態は保存しない。base と pending だけを持てば、
何度読み直しても同じ結果になる（二重計上しない）。

- `src/data/ops.ts` … 操作を値にする。`applyOp` は**通信しない純粋な関数**で、
  何度適用しても結果が変わらない（再適用できる）。
- `src/data/outbox.ts` … base と pending を端末に残す。タブ間の送信権も持つ。
- `src/data/cloudSync.ts` … 1件ずつ送る。失敗を「やり直す／諦める」に分ける。
- `src/data/useAppData.ts` … 上を束ねる。

### 書き込み

1. その場で画面へ反映（`replay` に載る）
2. 同じ操作を outbox に積んで**端末へ書く**
3. 送信は裏で。失敗したら間隔を空けてやり直す

**新しいスナップショットが届いても、未送信の操作はその上に載せ直す**ので、
入力中の値がサーバーの応答で巻き戻ることはない（原因4の解消）。

連続する変更（目標値・セット・食事の編集）は
- outbox の中で1件にまとめる（`enqueue`）
- さらに **500ms 手が止まってから**送る（`WRITE_DEBOUNCE_MS`）

の2段で、打鍵ごとの書き込みを止める。記録自体は打った瞬間に
端末へ書けているので、待っても失われない。

### 読み込み

起動時は**本人確認とスナップショット取得を同時に始める**（順番にやると往復2回ぶん待つ）。
前回クラウドで使っていたことは端末が覚えているので、確認を待たずに取りに行く。
人が違っていたら捨てて取り直す。

控えがあれば**通信を待たずに**表示し、裏で取り直す。

### id の張り替え

オフラインで「種目を足す→セットを足す」をすると、セットの操作は
まだ存在しない仮の種目 id を指す。種目の送信が通って本物の id が分かった時点で、
後続の操作を張り替えてから送る（`remapOp` / `remapData`）。

### 二重登録を防ぐ

- 端末が決めた仮 id を**そのまま冪等キー**にする（`clientRequestId`）
- 同じ送信待ちを複数のタブが同時に流さない（`outbox:lease:v1` の送信権）
- 画面を離れるときに送信権を手放す。手放さないと、
  再読み込み後しばらく送信できなくなる

### 保存できていないものを保存済みと言わない

`src/components/SyncStatus.tsx`。普段は何も出さず、

- 送信中 … 「保存中」
- 送り終えた直後 … 「保存済み」を少しだけ
- 送れずに残った … 「未同期 N件・通信が戻ると自動で保存します」
- 諦めた … 赤で知らせ、やり直すか捨てるかを選べる

ログアウトは端末の控えを消す操作なので、
**未送信があるときは件数を見せて確認する**（黙って捨てない）。

### 保存の重さ

控え（base）は半年ぶんで 190KB。操作のたびに JSON 化すると画面が固まるので、
**pending は毎回すぐ書き、base は間引いて書く**（画面を離れるときに書き切る）。
base はサーバーから取り直せるので、多少古くても実害が無い。

## 4. 話して記録する入口

    スマホの音声/文字
      → POST /api/v1/command
        → 振り分け（言語モデル 1回）
        → 検証（**MCP と同じ入力schema**）
        → 実行（**MCP と同じ道具**）
      → 結果 + 取り消し

`api/_v1/command.ts` は振り分けるだけで、業務の判断を持たない。
振り分け先は `api/_mcp/tools.ts` の `TOOLS` をそのまま使う。
**schema を二重に持たない**こと自体が、ChatGPT 経由と画面経由で
挙動がズレないための仕掛けになっている。

対象は `log_meal` / `log_weight` / `log_workout` /
`get_today_summary` / `get_recent_workouts` / `get_progress` の6つ。
**削除・目標変更・アカウント操作の道具はそもそも存在しない**ので、
音声から消すことはできない。

- 言語モデルの呼び出しは1指示につき**1回**。
  食事のカロリー推定もその1回に含める（別呼び出しにしない）
- 鍵はサーバーにしか無い（画面の束には入らない）
- 新しい鍵は要らない（既存の `OPENAI_API_KEY`）
- 推測すると間違えるときは**実行せずに聞き返す**
  （「60キロ10回」だけなら種目を尋ねる）
- 聞き取った文字列を必ず画面に出す。食事はその場で取り消せる

### 音声の取り方（2026-08-17 改訂：キーボードを開かない）

当初は「文字入力欄に focus → iOS キーボードのマイクキー」を本命にしていた。
`webkitSpeechRecognition` が **Safari のタブでは動くが、ホーム画面に追加した
PWA では動かない**（Apple 未対応）ためで、これ自体は今も正しい。

しかし実機で使うと、**緑のマイクを押すとキーボードが開く**。
求めていたのは「押したらそのまま喋れる」ことなので、作りを変えた。

    緑のマイクを1タップ（＝許可を求めてよい合図）
      → getUserMedia + MediaRecorder で PWA 自身が録音（キーボードは開かない）
      → 無音で自動停止（効かない端末は停止ボタン）
      → POST /api/v1/transcribe（音は base64、鍵はサーバーだけ）
      → gpt-4o-mini-transcribe（language: ja ＋ 筋トレ語彙の手がかり）
      → 文字 → 同じ振り分け（/api/v1/command）

端末差は**決め打ちせず feature detection で吸収する**。

- 録音形式は `MediaRecorder.isTypeSupported` に聞いてから決める
  （iOS は `audio/mp4`、Android/PC は `audio/webm;codecs=opus` が多い）。
  どれも通らなければ**指定せずブラウザに選ばせる**
- `getUserMedia` / `MediaRecorder` が無い端末では録音ボタンを出さず、
  文字入力（キーボードのマイクキー）へ落ちる
- 停止・失敗・画面を閉じる、のどの経路でも `MediaStreamTrack.stop()` を通す
  （呼ばないと iOS は録音インジケータが出たままになる）

音声そのものは Appwrite にも localStorage にも通常のログにも**残さない**。
変換のあいだメモリを通り過ぎるだけ。

#### iOS の癖への備え（実機で踏む前に手当てした3つ）

1. **形式は mp4 を先に試す。** WebKit が webm を録れるのは Safari 18.4
   （2025年3月）以降で、`isTypeSupported` が true でも `start()` が
   失敗する報告がある。iOS でいちばん枯れているのは mp4 なので、
   対応していると答えても新しいほうを優先しない
   （<https://webkit.org/blog/16574/webkit-features-in-safari-18-4/>）
2. **`stop()` しても `onstop` が来ないことがある**（空の録音になる）。
   `start(1000)` で1秒ごとに受け取っておき、`stop()` から1.5秒待っても
   合図が来なければ**手元のぶんで組み立てる**
   （<https://developer.apple.com/forums/thread/694207>）
3. **音声処理はタップの流れの中で作る。** iOS は許可ダイアログの「許可」を
   user gesture として扱わないため、`getUserMedia` を待ってから
   `AudioContext` を作ると止まったままになり、波形がぴったり無音で返る。
   先に作っておき、さらに「完全な無音かつ context が動いていない」ときは
   無音判定を使わない（喋っている最中に切らないため）
   （<https://bugs.webkit.org/show_bug.cgi?id=180522>）

なお iOS の PWA では**マイクの許可が保存されない**（起動ごとに聞かれる）。
これは Safari 側の仕様なので、こちらでできることは無い
（<https://bugs.webkit.org/show_bug.cgi?id=215884>）。

文字入力欄は「聞き取りを直す」ために残すが、**開いた時点では focus しない**。

実装: `src/utils/recorder.ts`（録音）/ `api/_v1/transcribe.ts`（文字起こし）/
`src/components/VoiceCommand.tsx`（画面）。

出典:
- <https://whatpwacando.today/speech-recognition/>
- <https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide>

### 話しことばの揺れを吸収する（実機で出た失敗の修正）

実機で複数種目を自然に話すと、画面に
`Invalid input: expected number, received undefined` が出ていた。原因は2つ。

1. **内部の検証文言をそのまま画面へ出していた**（`command.ts` が zod の
   `issue.message` を本文に埋めていた）
2. `log_workout` の schema は全セットに `weight` を必須にしているが、
   言語モデルは自重種目の重量を書かない（「懸垂8回と7回」）。
   セットごとに違う値を言うと後半の `reps` も落ちる

そこで**検証の手前に正規化層**を置いた（`api/_v1/normalize.ts`）。

直すもの（言い方の揺れ）:

- `sets: 3` のような省略形、`"70kg"` のような文字列、全角数字
- **自重種目の重量を 0 にする**（schema 側の「自重なら0」と同じ意味。
  対象は懸垂・腕立て・腹筋など、名前で判定できるものだけ）
- 同じ種目で重量が省かれた続きのセットは、直前のセットの重量を引き継ぐ

直さないもの（**推測せずに聞き返す**）:

- 回数が無い → 「ラットプルダウン65kgは何回ですか？」
- 種目名が無い → 「60kgはどの種目ですか？」
- 加重種目の重量が最初から無い → 「ラットプルダウンは何kgですか？」

正規化を通ってもなお schema を外れた場合は、`explainIssue` が
**日本語の短い聞き返しへ言い換える**。zod の文言が画面へ出る経路は無い。
指示文（プロンプト）にも、複数種目・セットごとの違い・自重の書き方を明記した。

### 音声の記録も local-first を通る

`/api/v1/command` に `apply: 'client'` を付けると、**サーバーは保存せず**
「何を保存するか（plan）」だけを返す。画面はそれを既存の操作
（`addExercise` / `addSet` / `addMeal` / `saveWeight`）に変換して積む
（`src/data/voiceOps.ts`）。つまり音声の記録も

    その場で画面へ反映 → outbox に積む → 裏で送る

という同じ道を通る。音声のときだけ通信を待つ、ということが起きない。
`apply` を付けない呼び出し（ChatGPT 経由・古い画面）は**今までどおり
サーバーが保存する**ので、MCP は凍結したまま影響を受けない。
